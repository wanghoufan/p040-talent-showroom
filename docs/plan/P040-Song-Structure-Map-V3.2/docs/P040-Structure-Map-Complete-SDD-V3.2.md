## 1. 产品定义与设计冻结

### 1.1 目标体验
1. 唱歌详情第一屏先看到**歌曲地图**，例如：`前奏 → A1 → P1 → B1 → A2 → B2 → C1 → B3 → 尾奏`；符号语义：A=主歌、B=副歌、P=预副歌、C=桥段、R=人工确认的 Rap，末尾数字=该类型第几次出现。**A2≠已确认与 A1 旋律一样，B2≠已确认与 B1 旋律一样**；重复关系必须有可查证证据。
2. 点击段落立即定位原有播放器时间轴，歌词区域切换显示本段歌词；选择**整段循环/退出**，保持逐句循环（2/4/自定义）、变速、原唱/已有伴奏切换、合练。
3. 听辨觉得某段不对时，直接点击歌词中某一行作为拆分点；“合并上一/下一段”和“类型修改”一键可用。保留高级的秒数精调，但不作为默认操作。编辑支持撤销、预览及显式确认；不得在 UI 中强行滚到很远的表单。
4. 相似段落显示“候选相似（待确认）”，手动可选“同旋律同歌词 / 同旋律换歌词 / 不同”。只有经确认的重复关系才能在“先学一次、后续复习”中复用。
5. Rap 检测不足时显示“待确认”，**不显示 Rap 百分比**；未确认的 Rap 不参与自动跳过。演出模式不继承练唱跳 Rap 或循环设置。
6. 手机约 390dp 单列，紧凑两列/四列段落网格，默认浅色、可切深色，底部原四 Tab。不要另起“歌曲地图”一级 Tab，也不要做 PC 宽屏左右分栏。

### 1.2 正确的数据职责
- **音频原曲**：提供节拍/乐段边界/伴奏编配与和声特征。结构角色可由经过验证的模型给出，或在不知道时明确标“待标注”；不能让重复歌词强行判定主副歌。
- **LRC**：只负责歌词文字、句序和时间锚点（用于跳转、定位拆分、比对歌词），不能单独判定旋律或 Rap。
- **声学相似度**：从原曲混音音频提取 CENS/Chroma/自相似矩阵得出可能重复候选；和弦相似可能造成误判，不能直接叫做“同旋律”。
- **人的确认**：最高优先级，已校正的段落永不被自动分析覆盖。结构类型与重复关系各自有独立的确认状态。

## 2. 技术路线：绝不把音源分离当作隐藏前置步骤

### 2.1 允许的本地基础路径（立即执行）
`用户已有原唱 MP3（只读） → ffprobe/ffmpeg 解码直接读取混音 → librosa beat/chroma/recurrence/novelty → 自动建议段落边界与音频相似候选 → 和原 LRC 时间戳关联 → 形成不覆盖正式字段的结构草稿 → UI 人工快速校正 → 显式应用到现有 sections API`。

首阶段先做到边界候选和重复候选。若缺可靠的乐段角色模型，应显示 `U1/U2` 待标注或让用户快速选择主歌/副歌；**不要假装 librosa 已自动认准主歌、副歌或同旋律**。`src/direct_mix_similarity.py` 已提供可运行的“原曲混音声学相似候选”起点；仅作为候选，不提供完美旋律识别承诺。

### 2.2 可选结构模型验证（必须先检查无分离行为）
- `mir-aidj/all-in-one` 官方能输出 BPM、beats、downbeats、`segments(start/end/label)`，但原始方法围绕 demixed audio；Mac GPU 移植 `all-in-one-mlx` 官网明确默认包含 Demucs demix。**本轮不得直接执行默认 CLI**。只有确认某个版本有“直接分析原曲、完全跳过 demix”的合法入口，并能通过子进程追踪证明未启动分离器，才允许把其输出作为候选；否则继续用直接混音路线 + 人工确认，不能为了提高分类率违背暂停要求。
- 不购买云模型、不上传 MP3 到外部服务、不下载不必要权重。若需要联网获取结构模型权重，先说明来源、许可、大小和替代，未经许可不要让它自动下载。

### 2.3 真实评分原则
在用户已有 20 首中，优先 5 首进行定向人工听辨对照：
1. `初爱`（中文慢歌，常规主副歌）
2. `Let Go`（英文，旧算法切成 22 段）
3. `Papillon`（英文/Rap，避免误分）
4. `베베 (BABE)`（韩文，副歌重复）
5. `senorita (翻自 Shawn Mendes)`（英文翻唱，旧算法切 29 段）

每首记录人工标注边界、结构类型、旋律关系（可标不确定）；以逐首表格比较旧算法 vs 新方案，至少统计：边界 ±2 秒内的查准/查全；主歌/副歌类型查准；重复候选 precision；超碎片化率；未确定关系数量；在 M4 的处理时间、内存。建议目标：边界 F1 ≥0.8、主副歌分类正确率 ≥0.75、重复候选确认 precision ≥0.85、单曲无明显界面卡顿；**这些是内部验收目标，不是已取得成绩，也不能拿合成音频打分**。达不到先优化分析和交互，不批量覆盖真实结构。

## 3. 结构数据与兼容性

### 3.1 草稿与正式字段隔离
- 现有服务端 `repertoire_items.sections_json` / `lyrics_json` 和 `src/lib/types.ts` 的 `VocalSection` 是正式用户数据，不直接替换；V3.2 单独保存 `songId + 原曲 SHA256 + modelName + modelVersion + generatedAt + proposedSegments + relationCandidates + notes + state`（优先新增表/本地 sidecar JSON，按 P040 现有库规范决定）。
- 未审核结构一律状态 `DRAFT/NEEDS_REVIEW`；经用户**明确保存**才通过 `saveRepertoire`/离线编辑队列写回正式字段。若用户编辑后断网，应沿现有离线同步队列与冲突检测实现。
- 保存前对旧结构做独立版本备份，在隔离库验证 `revision` CAS/冲突处理。保留旧分析结果与人工改动，允许恢复，不进行破坏性数据库迁移。
- 正式字段结构 `[{id,type,label,startMs,endMs,source,repeatOf?,repetition?}]`；`label` 为 A1 等，`type` 保持现有枚举。当前服务端拒绝客户端自行传 `source:'algorithm'`，**用户确认后写回全部标记 `source:'manual'`**，而 AI 生成来源保留在独立分析草稿；不可硬改服务端权限规则。
- 已有 20 首的旧自动结构不可直接删除。后台生成 V3.2 草稿，与旧图并列预览；只有用户接受新图，才更新对应曲目。手工校准过的旧结构始终优先。

### 3.2 重复关系
- A/B/P/C 的数字仅代表对应结构类型第几次出现，并不等价于旋律相同。相似度结果仅保存 `from/to/score/method/status=pending-confirmation`。
- `same-melody-new-lyrics` 与 `exact-lyrics` 为人工确认结果。确认为“同词”还要对比对应 LRC 文字；不同不能存 `exact-lyrics`。
- Rap 必须人工确认时间区间后才可参与练唱“跳过 Rap”，合练选择不影响演出模式。
- `split/merge/type/relationship` 均保留历史并可 Undo/Redo，严防引用断裂 `repeatOf` 悬空。

## 7. 风险、依赖、不可自动跨越的边界

- 结构模型（尤其 all-in-one-mlx）默认可能先调用源分离，**当前暂停状态禁止启用该路径**；若直接混音模型无法给可靠副歌标签，保守地先给待标注，不作“自动精准分类”虚假承诺。
- Chroma/和弦重复会误判成旋律重复：候选只能用于提醒，人工听辨才确认；Rap 的识别不能偷换成时长或声学重复检测。
- 测试素材由 Mac mini 在现有本地原始目录直接只读读取，**不可上传原曲到公开仓库、插件或在线服务**，也不要求用户重新提供 MP3。
- 正式 APP 工作树未提交，生产 DB 旧版本；必须用隔离副本开发，并保存历史结构迁移前后 diff。真机只能使用用户授权设备，不碰项目零操作红线设备。
- 用户最终验收关心“真正学得快、段落关系看得懂”，不只是模型跑得通。不能用这批演示数据宣称真实分类准确。

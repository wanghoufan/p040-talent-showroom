# 「播放没有声音」诊断（真机 note11tpro）

日期：2026-10-02　设备：192.168.31.63:5555（Redmi Note 11T Pro+ / 22041216UC / xagapro）

## 结论：App 播放链路正常，无声来自设备侧（媒体音量 0 + 音频被路由到录屏虚拟设备）

## 证据

App 侧（WebView 内 `document.querySelector('audio')`）：
- `volume=1`、`muted=false`、`paused=false`、`currentTime` 由 0 前进（19.46s 曲目）。
- `error=null`。
- 系统日志：`requestAudioFocus() ... AA=USAGE_MEDIA ... callingPack=com.wanghoufan.dancelibrary.dev`（App 正确申请媒体音频焦点）。

设备侧：
- `settings get system volume_music_speaker` = **0**（扬声器媒体音量为 0）。用 6 次 `input keyevent 24` 提升后 `dumpsys audio` 显示 `STREAM_MUSIC streamVolume:14`。
- `dumpsys audio` STREAM_MUSIC 段：`Devices: remote_submix(8000)`——当前输出设备是「远程子混音」（虚拟采集设备），非物理扬声器。
- `ps -A` 存在 `com.miui.screenrecorder`（MIUI 录屏进程在运行，录屏会占用 remote_submix 路由）。

## 说明

- 这不是产品代码缺陷，属设备音量/录屏路由状态。
- 需用户配合：停止 MIUI 录屏、确认媒体音量，再复听。
- 待用户确认“实际出声”后，本项方可记为通过。

## 补充复验（2026-10-02，audio_flinger 客观证据）

排除 dumpsys audio 的假象（020 教训：dumpsys 的 device 字段不可信），改看 `dumpsys media.audio_flinger` 的真实输出轨：

- App 播放中（CDP）：`paused=false`、`currentTime` 前进（4.12/19.46s）、`volume=1`、`muted=false`、`error=null`。
- flinger `AudioOut_BD` 线程：`Standby: no`、`Output devices: 0x8000 (AUDIO_DEVICE_OUT_REMOTE_SUBMIX)`、活跃轨 client pid=16190（= 本 App WebView）→ **App 声音确实被送进 remote_submix 虚拟采集设备，物理扬声器收不到**。
- 另有一个 `type 2 (DUPLICATING)` 输出线程处于活跃（音频复制/采集路径）。
- `dumpsys media_projection`：`(com.xiaomi.mirror, uid=1000): TYPE_SCREEN_CAPTURE` —— 投屏镜像进程持有屏幕采集会话；`am force-stop` 后短暂消失，随后**自动重注册**（系统包，`pm disable-user` 报 `Cannot disable system packages`）。
- 处置尝试：媒体音量已调到 15；已 `force-stop` + 禁用录屏包；两次停采集会话后重播，`AudioOut_BD` **仍钉在 remote_submix** → 音频策略/输出轨为卡死状态，adb 侧无法翻转。

## 结论（更新）

- 根因**已在设备侧客观坐实**（音频输出被劫持到 remote_submix），非 App 代码缺陷；020 的三类修法（seekTo 顺序 / 素材响度 / 音频会话）对 040 均不适用（技术栈不同，且素材响度已用 ffmpeg volumedetect 排除）。
- 该路由卡死需**重启手机**（或关闭系统「投屏/屏幕镜像」开关）方可复位；重启会断开无线 ADB，需用户配合，随后我再复验。

## 闭环（2026-10-02，重启后复验 · 已解决）

- 用户重启 note11tpro（重启后经 USB 接入，serial `IN9LZTAYV4UGU4JF` / 22041216UC）。
- 复验：`media_projection` 无任何采集会话；`volume_music_speaker=15`；App 播放中 `paused=false`、`currentTime` 前进、`vol=1`、`err=null`。
- flinger 真实输出轨 `AudioOut_15`：`Standby: no`、`Output devices: 0x2 (AUDIO_DEVICE_OUT_SPEAKER)` —— **输出已回到物理扬声器，REMOTE_SUBMIX 劫持消失**。
- 定论：`P0 播放没有声音` = 设备侧音频路由卡死（输出被钉在 remote_submix 虚拟采集设备），**重启已复位**；**App 代码无缺陷，无需任何改动**。此前将原因归到「录屏/投屏进程在跑」属误判（停进程后路由未变即证伪），已更正。
- 遗留：T064 物理断网冷启动（受网络/USB 条件限制，待现场）。

## 最终归因更正：scrcpy 默认转发音频（本次复发定位）

用户再次报告“接线后手机无声”，保持现场经 USB 读取：
- 固定真机 `IN9LZTAYV4UGU4JF` / `22041216UC`；STREAM_MUSIC 未静音，speaker 音量非 0，当前 Devices 为 remote_submix。
- Mac 正在运行 `scrcpy -s IN9LZTAYV4UGU4JF --stay-awake ...`，未指定 `--no-audio`。
- 本机 scrcpy 4.1 `--help` 明确说明 `--audio-source=output` 会转发整机声音并禁止设备本地播放；`--no-audio` 禁用音频转发。
- 用户确认：接线投屏时声音到 Mac，拔线后手机恢复播放。因此本次是投屏音频转发行为，不是应用播放故障。此前仅根据 remote_submix 将状态判为“必须重启的音频路由卡死”，证据不足；此前针对 MIUI 录屏/镜像进程的处置未覆盖 Mac 上 scrcpy 音频转发。

处置：仅终止核验的该手机 scrcpy 会话，保留原画面窗口位置并以 `--no-audio` 重开；未重启手机、未改 App/音量/真实数据。复验：设备仍 USB 在线，STREAM_MUSIC `Devices: speaker(2)`，streamVolume 10、Muted false；AudioFlinger 输出为 `AUDIO_DEVICE_OUT_SPEAKER`，不存在 REMOTE_SUBMIX 输出/输入采集行。

当前会话已禁用音频转发；未来重新开投屏需继续带参数，不能表述为已修改 scrcpy 全局默认：
`scrcpy -s IN9LZTAYV4UGU4JF --no-audio --stay-awake`

结论：本次 P0 无声反馈已解释并消除转发条件；用户确认拔线即正常出声，应用无须修改。真机 QA 用只传画面的投屏，避免将 Mac 出声/播放器时间前进当作手机物理扬声器验收。

## 1. 摘要：最关键的 5 条结论（V1.1 更新版）

1. **项目立项时是「方向待定」的空壳，真实 Day 1 需求是被事后追加的「个人舞蹈曲库 V1.5」，而非项目名「才艺展示厅」所暗示的多才艺形态。** 证据：`e198c06` 的 `README.md` 原文为「才艺展示厅项目；具体产品方向待后续明确」；首个实质提交 `2ca15cd` 才是舞蹈曲库 V1.5 全量 SDD。⇒ 命名与首个落地形态之间真实错位，是后续「补吉他/唱歌」重构的最大根源之一。**本轮经 B 交叉确认：此错位坐实，B G1 成立。**

2. **「多才艺（舞蹈/吉他/唱歌）」不是 Day 1 设计，而是分三次规格迭代叠加出来的**：`001` 仅舞蹈 → `002`（`ca2c3d8`）追加吉他+唱歌（最小版，且**无 spec.md**） → `003`（`8fd92c9`）三才艺完整化（亦**无 spec.md**）。每次都是独立规格分支。⇒ 若 Day 1 就能把「才艺库」的多类型抽象（`ItemRef`、独立主表但统一引用）写进基线，可显著减少 `002/003` 的「不把旧 DanceItem 硬塞进全才艺实体」式返工。**本轮补充 B 洞察：002/003 缺形式化 spec.md（G2），使"完成"靠开发者自述而非可追溯 AC——这是 A V1.0 遗漏的验收形式化缺口。**

3. **离线优先（Offline-first）是 Day 1 就锁定的真需求，但「原视频离线也能播」是后来（2026-10-12 `a03dcdf`）才推翻早期非目标补上的。** 早期 `003` 计划明确写「原始视频继续不批量缓存」；后来才做成断网可播。⇒ 这是一条「后来才明确」且**曾与早期非目标冲突**的需求，值得在 Day 1 提示词里主动问清楚。

4. **【V1.1 修正｜重大】"伴奏/音源分离"绝非 Day 1 就已知的"明确不做"硬边界——A V1.0 的"从头到尾是用户明确指令的不做项"表述**overstate**了。** 经核查：Day 1（`e198c06`/`001` spec）无任何伴奏相关约束；V3.1（`tool/run_separation.py`、SDD line4「正式术语：AI 人声分离/伴奏提取」）反而把伴奏提取当作"待主开发者在 M4 预检后执行"的功能来设计；直到 **V3.2（2026-10-30）** 才首次以"用户最新指令：伴奏生成先暂停"显式暂停/不做（V3.2 SDD line3、README line6、Handoff line3）。⇒ 正确结论应是：**"不做伴奏"是 V3.2 才由用户新指令确立的边界，不是 Day 1 前提；但 V3.1 在动手设计整套分离工具前未与用户书面确认"做不做"前提，属"迭代中才澄清的边界 + 可预防的前提确认缺口"，而非 B 所称的"Agent/流程失误"（应降级）。** 这直接修正 A V1.0 §1.4、§6.2、§9 的措辞。

5. **四态严重错位，且错位在本轮取证时进一步恶化。** 已部署到用户手机的调试包 APK（现 HANDOFF 记 1.1.11/14 已出、早期 1.1.10/13 已装；而本工作树 `build.gradle` 已到 `versionCode 15/1.1.12`）实际由**含未提交代码的工作树**构建，因此"已部署态"远超"已提交 HEAD（`eb748f7`，`versionCode 9/1.1.6`）"；而"用户最终认可态"中"首次发布签收"仍为 OPEN，且 5 首真实听辨、生产库迁移从未执行。⇒ 不能笼统说"最终产品"，必须区分四态（见第 2 章）。**【V1.1 修正】B G10 的"未提交即部署"事实成立，且比 B 快照时更严峻：本工作树现 78 项未提交（B 当时 77 项）、versionCode 已到 15；仅 `eb748f7` 一个提交触碰 build.gradle，故所有 1.1.7–1.1.15 调试包均来自未提交树，不可复现/回滚。B 归为"Agent/流程失误"成立，但精确归类应为"可追责性/可复现性治理失效"，非"返工"。**

## 3. 二、完整使用旅程（从成熟形态反推）

下面按"真实被使用过"的线索（验收矩阵、HANDOFF、源码页面）还原完整旅程。项目有两类角色：**主人/主用户**（持 Mac + 手机，管理曲库）、**访客**（扫码点歌，仅 003 阶段 6 设计、部署留 Human Gate）。

### 3.1 旅程总览（主人视角）

```
[收录] → [整理/分类] → [练习] → [今晚节目单] → [现场演出] → [点歌台(可选)]
   │           │           │                          │
   └─Android 分享/本地文件/手动音频+封面    └─离线准备/断网演出
```

底层始终依赖：**Mac Mini 本地服务（收录/FFmpeg/识曲/SQLite/同步 API）+ 手机 Capacitor App（UI/离线缓存/分享接收/现场播放）**，信任局域网同步，无云账号。

### 3.2 分场景旅程

**场景 A — 第一次打开就收录第一支舞（US1，P1）**
- 空库首屏即有固定标签框架 + "+ 收录舞蹈"；不要求登录。
- 收录入口区分"收的是舞"：Android 提供「抖音/分享链接收录、选择手机视频、手动音频+封面」；桌面额外拖入/选择文件。
- 自动流程依序反馈"获取视频/提取音乐/识别歌曲/获取封面/生成曲目"，不暴露 ffmpeg/provider 细节。
- 确认页可试听实际提取音频、看歌曲候选、看"查看原视频"入口、默认"想学"、0~4 场景标签。
- 识曲/封面失败仍可用来源截图/占位图保存。
- 证据：`specs/001-personal-dance-library/spec.md` US1/US2/FR-001~FR-012。

**场景 B — 保存短视频里真正跳舞用的声音（US2，P1）**
- 默认保留整段来源音频，不自动变速/升降调/响度标准化。
- "调整音乐片段"只拖 start/end、试听、恢复完整；裁剪不覆盖 SourceMedia；识曲元数据更新不替换 PerformanceClip。
- 来源不兼容时允许一次 AAC 兼容转码，时间轴/速度/音调保持。
- 证据：`spec.md` US2、FR-008/009；`plan.md` Import Pipeline（EXTRACT 首选 stream copy）。

**场景 C — 用 3 状态 + 4 场景快速找（US3，P1）**
- 左侧"会跳/正在练/想学"单选；顶部"耍酷/性感/户外/转场"多选 AND。

- 证据：`spec.md` US5、FR-014/015、SC-004/005/010。

### 13.2 收录→演出 端到端最小路径（主人，含真实端点）

依据 `specs/001.../plan.md` API Contracts 与 `server/routes/*`、验收矩阵：

```
[Android 分享/本地文件]
   → POST /api/imports/file 或 /api/imports/link   （建 ImportJob）
   → 服务端 ACQUIRE→PROBE→EXTRACT→RECOGNIZE→COVER→REVIEW→FINALIZE
       · EXTRACT 首选 stream copy（ffmpeg -c copy），不兼容才 AAC 转码
       · RECOGNIZE 只传最小短音频，无 key 则 mock
   → GET /api/imports/:id 轮询状态机（PENDING/PROCESSING/NEEDS_INPUT/READY/FAILED）
   → POST /api/imports/:id/finalize 落库（DanceItem + SourceMedia + PerformanceClip + SongIdentity）
[整理]
   → GET /api/catalog（按 状态/场景 筛选，AND 语义）
   → PATCH /api/dances/:id（改状态/标签）
[今晚节目单]
   → GET/PUT /api/playlists/tonight（{kind,id} 引用；003 起混合）
   → "准备离线演出"：按 offline-manifest 下载并核验 size/hash，置 Ready
[演出模式]
   → GET/HEAD /api/media/audio/:clipId（不透明 ID，拒绝绝对路径）
   → 离线冷启动从 catalog.json + offline-manifest.json 读本地快照
   → 自然结束停，不连播
```

证据：`specs/001.../plan.md` "API Contracts" 与 "Import Pipeline"；`server/index.mjs` + `server/routes/`、`server/import/`；验收矩阵 AC-V31-QA-01（拒绝绝对路径）、AC-V31-QA-08（4 类路径攻击 403）。

### 13.3 唱歌双音轨的真实数据流（V2.1/V3.1 → V3.2 翻转）

```
V2.1/V3.1：
导入一首歌 → server/vocal-import 扫描配对 mp3 + lrc
   → 分离器（假/真 audio-separator）产出 原唱 + 伴奏 两轨（V3.1；run_separation.py 默认 dry-run）
   → repertoire_items 关联 source_media/performance_clips
   → 歌词 LRC 时间轴 +（V3.2）音频分析段落 A1/A2/B1/B2/C1
   →（V3.3）译文层 translations_json 与原文 lyrics_json 分离
练习/演出：VocalPracticePlayer 控原唱/伴奏切换、点句、循环、跳 Rap、合练

V3.2 起（用户指令暂停分离）：
   → 仅用原唱混音做结构分析（direct_mix_similarity.py，librosa chroma_cens，不分离）
   → 双轨中的"伴奏轨"对真实歌曲实际不再生成；演出默认伴奏退化为仅原唱可练
```

**【V1.1 关键洞察】** 唱歌"双音轨演出"这一用户旅程，在 V3.1（计划做分离）与 V3.2（暂停分离）之间存在策略翻转。这意味着：若 Day 1 就把"双音轨"当确定需求，会在 V3.2 被迫接受"仅原唱"。更稳妥的 Day 1 表述应是"唱歌需要原唱/伴奏切换能力，但伴奏从哪来（分离提取 vs 用户自备 vs 不做）是待确认前提"——这正呼应 §12 冲突 1 的"动手前先确认做不做"。

证据：`docs/plan/P040-Vocal-KTV-Five-Songs-V2.1/README.md`；`P040-Local-AI-Import-V3.1/README.md` + `tool/run_separation.py`；`P040-Song-Structure-Map-V3.2/docs/P040-Structure-Map-Complete-SDD-V3.2.md` line3/13/31；HANDOFF:13。

### 13.4 同步与冲突的真实机制（003 阶段 5，常被忽略的设计）

- 服务端给记录/节目单加 `revision`；同步请求带 `operationId` + `baseRevision`；重复请求不重复执行。
- 版本冲突：保留手机草稿 + 服务器版本，不自动覆盖，集中放"我的→同步待处理"，用户逐字段合并。
- 证据：`specs/003-talent-library-completion/plan.md` 阶段 5；验收矩阵 AC-V21-07。

## 2. 差距证据链（核心：12 个高价值需求差距）

每个差距按"七问"展开：**① 原来怎么说 → ② 后来实际怎样 → ③ 差在哪里 → ④ 为何本应提前思考 → ⑤ 不提前造成何种返工 → ⑥ 下次普通人怎么说 → ⑦ 提前明确的收益**；并标注**责任分类**（用户应表达 / 顾问·计划者应主动发现 / 开发者负责）与**返工分类**（可预防 / 正常迭代 / Agent 或流程失误）。

### G1｜立项名"才艺展示厅"暗示多才艺，但首规格只做舞蹈

① **原来怎么说**：立项 `README.md`（`e198c06`）"具体产品方向待后续明确"；项目名"才艺展示厅"字面含"才艺"复数义。
② **后来实际怎样**：首个落实规格 `specs/001` 仅舞蹈（`个人舞蹈曲库 V1.5`）；吉他+唱歌在 10-03 的 002 才追加，三才艺完整化在 003 才收口。
③ **差在哪里**："才艺展示厅"之名与"仅舞蹈"之实不一致；名称埋下的多才艺预期未在立项当天澄清，导致舞蹈先单独成规格、才艺后两次叠加。
④ **为何本应提前思考**：项目名是用户给的第一信号；顾问/计划者应在第 1 天就追问"才艺展示厅 = 只舞蹈，还是舞蹈+吉他+唱歌多形态？"，而不是先写单才艺规格。
⑤ **不提前造成何种返工**：001 按单才艺设计数据模型与 UI（四个固定场景标签、DanceItem 实体）；002/003 必须把架构硬扩成多才艺（独立 `repertoire_items`、混合节目单、ItemRef 抽象），部分 UI 与接口返工。属**正常迭代为主 + 部分可预防**（若第 1 天澄清范围，002/003 可合并为一次性规划，省一轮叠加）。
⑥ **下次普通人怎么说**："我要做个才艺展示厅，先想清楚：到底是只管舞蹈，还是要同时管舞蹈、吉他、唱歌好几样？别先写死成只跳舞。"
⑦ **提前明确的收益**：避免单才艺规格先行、多才艺后补的两轮叠加；架构一次到位，少一次重构。

- **责任分类**：用户合理应表达（范围）+ 顾问·计划者应主动发现（追问"才艺展示厅"含义）
- **返工分类**：正常迭代（部分）／可预防（部分）

---

### G2｜001 规格严谨有 User Story+SC，002/003 扩展却无形式化 spec.md

① **原来怎么说**：001 `spec.md` 含 8 个 User Story、独立 Test、FR-001~028、SC-001~010 可量化成功标准，验收口径清晰。
② **后来实际怎样**：`specs/002-guitar-vocal/` 仅有 `plan.md`/`data-model.md`/`tasks.md`/`contracts.yaml`，**无 `spec.md`**；`specs/003-talent-library-completion/` 同样无 `spec.md`（仅 `plan.md`/`data-model.md`/`tasks.md`/`contracts/openapi.yaml`）。
③ **差在哪里**：才艺扩展（占最终功能大半）的需求未被同样严谨地"验收口径化"；002/003 的"完成"靠 `HANDOFF.md` 文本叙述与测试清单，而非可追溯的 Acceptance Scenario。
④ **为何本应提前思考**：每扩一个才艺都是一次"新规格"，应复用 001 的规格模板（用户场景→验收→可量化 SC），否则验收口径随规模膨胀而稀释。
⑤ **不提前造成何种返工**：后期验收无统一标尺，出现"功能写了但验收靠开发者自述"的情况（如 §2.G6 UI 走查缺失、§5.1 深浅色待验证）；返工为**可预防**（扩展也该有 spec）。
⑥ **下次普通人怎么说**："每加一种才艺，都按第一版那样写清楚：用户场景、验收条件、能打分的成功标准，别只写个计划就开干。"
⑦ **提前明确的收益**：验收口径一致、可审计；避免"做完了但说不清算不算完"的扯皮。

- **责任分类**：顾问·计划者应主动发现
- **返工分类**：可预防

### G3｜"不把旧 DanceItem 硬改成全才艺实体"在 003 才书面明确

① **原来怎么说**：001 的 `DanceItem` 是"一支具体编舞"的强类型实体（spec.md Key Entities）。
② **后来实际怎样**：002 已先建独立 `repertoire_items`（kind=GUITAR/VOCAL），未硬改 DanceItem；003 `plan.md` §8 才书面确认"保留 `dance_items` 和 `repertoire_items` 独立主表，不把旧 DanceItem 强行改成包含全部才艺的实体"。
③ **差在哪里**："分表 vs 统一实体"这一关键架构决策，在 001→002 过渡时未提前澄清，靠 003 事后追认；002 虽未走错路，但决策过程是"先做了再看对不对"。
④ **为何本应提前思考**：数据模型是返工成本最高的决策；多才艺扩展第一刀就该明确"复用还是分表"，否则 DanceItem 一旦被改成全才艺实体，后续所有迁移与 UI 都要重写。

⑤ **不提前造成何种返工**：属**正常迭代（合理留 gate）+ 可预防（应提前讲清"本地可用≠公网可用"）**——若不讲清，用户会在"没上线"时误以为"坏了/没做完"。
⑥ **下次普通人怎么说**："这一版是只能在家里的网用，还是别人也能上网点？你直接告诉我边界在哪，别让我自己猜。"
⑦ **提前明确的收益**：发布边界预期一致，减少"以为上线实则未发布"的误解与催促。

- **责任分类**：顾问·计划者应主动说明 + 用户合理应表达（理解边界）
- **返工分类**：正常迭代 + 可预防（部分）

### 5.3 一次性交付与真实 QA（按 §5.3 要求：追溯"为何看似完成仍返工"）

**为何"功能看似完成、实际仍返工"的根因链**：

1. **缺真实样本**：V3.1 真实 MP3 所在外部卷未挂载（QA-Results 自承 "external-volume path is not mounted"），真实样本从未进入验证；V2.1 用原创 demo 五首替代用户真实节目单五首（G5）。
2. **只测成功路径**：V3.1 "31 项自动化测试通过"但"未修改真实数据库/源码、未实测音质"；单测绿 ≠ 真实可用。
3. **未覆盖异常与断网**：001 spec 列了详尽 Edge Cases（无音轨/损坏/超大/伪 MIME/识曲超时/重复 intent 等），但 HANDOFF 未提供这些异常路径的真机/集成证据清单（推断：异常路径验收待补）。
4. **未做真机/多端**：V3.1 "No real Android device was operated"；V1.2 "未上手机"——Web/构建通过但 Android 真机零走查。
5. **已发布版本与本地代码不一致**：四态错位（G10）——部署 APK 来自未提交工作树，与已提交 HEAD 不等价，回滚/复现无解。
6. **缺少人工确认**：首次发布签收 OPEN（Human Gate 设计如此，但意味着"用户认可态"未达成）；真实五首听辨未出声（G5）。
7. **验收口径不明**：002/003 无形式化 spec（G2），"完成"靠开发者自述而非可追溯 AC。

**结论**：一次性交付的质量黑洞，本质是"验收口径（真实样本+真机+异常+用户签收）未前置为硬 gate"。补这一 gate，可将多数返工从"事后爆发"转为"事前拦截"。

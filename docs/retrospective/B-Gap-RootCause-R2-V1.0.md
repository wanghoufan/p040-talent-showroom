## 3. 本轮新增差距证据链（七问逐项）

### G-R2-1 ｜「已生成 PDF」假通过：提示当验收、矩阵不回写

1. **原来怎么说**：AC-PRINT-05 判据写「点『下载 PDF』提示『已生成 3 页 PDF』，无错误态」，矩阵记 PASS（`docs/qa/产品验收追踪矩阵.md:275`；`evidence-2026-11-04-v13-r2/QA_RESULT.md:38`）。
2. **后来实际怎样**：项目自己的踩坑库早已写明「界面提示『已生成 PDF』不等于文件存在——Capacitor WebView 不处理 blob 的 `a[download]`，字节只在内存里」（`agent.md:42`）；随后 R3 任务把「修复 Android WebView Blob→a[download] 假成功」列为 P0（`CURRENT_TASK.md:25`）；最终 11-08 用户直接否决手机端 PDF（`HANDOFF.md:5`）。矩阵该行至今仍为 PASS、未回写 FAIL/作废（Grep 全文仅 :275 一处）。
3. **差在哪里**：验收判据写的是「表象」（提示无错误态），不是「结果」（设备文件系统找得到文件、外部应用可打开）——而后者 `agent.md:42` 在本轮之前就已立为判据。判据与判据之间没人对账。
4. **为何本应提前思考**：本项目是 Capacitor WebView，`a[download]` 假成功是平台已知行为，A4/PDF 需求立项时判据就该按 agent.md 既有铁律写。
5. **不提前造成何种返工**：一轮 R3 P0 修复计划（含原生 PdfSavePlugin 开发）＋专项 QA；更糟的是一条假 PASS 进了对外追踪矩阵，构成「验收留痕失真」。
6. **下次普通人怎么说**：「手机上到底存没存出文件？文件管理器里找得到、能打开吗？别只说提示成功了。」
7. **提前明确的收益**：把判据一句写对，可省一轮 P0 修复与一次假签收；若同时先问「手机端要不要 PDF」，整段代码（`src/native/pdf-save.ts` 等）都不必写。

### G-R2-2 ｜脏树出包复发：1.1.24–1.1.32 十个版本未提交即装机

1. **原来怎么说**：L1 定案「任何要装到用户手机的包必须来自已 commit 的 HEAD」（`Project-Lessons-V1.0.md:28`）。
2. **后来实际怎样**：11-04～11-08 连续产出 1.1.24(27)～1.1.32(35) 共约十个版本、装机三台，期间三份 QA 回执自记「未 commit、未 push」（`evidence-2026-11-07-loop-rap/QA_RESULT.md:79,100`、`evidence-2026-11-08-auto-pair/QA_RESULT.md:34`）；直到 11-08 `24d6b8f` 一次性提交收尾（`HANDOFF.md:6`）。
3. **差在哪里**：上一轮的教训沉淀为「教训」但没有变成「机器闸门」——出包链上没有任何一步检查 `git status`；bump 脚本（`scripts/bump-android-version.mjs`）只管版本号递增。
4. **为何本应提前思考**：上一轮复盘刚判过同类问题（1.1.7–1.1.15），同型风险应直接进体检表并脚本化。
5. **不提前造成何种返工**：期间任何一次误 `reset/clean` 都会不可逆丢失已装机版本的源码（旧风险 `docs/risks.md:29`）；追溯"用户手机上 1.1.29 到底对应哪份代码"只能靠 QA 回执反推。
6. **下次普通人怎么说**：「装到手机上的版本，代码先存进仓库了吗？还是又攒了一堆没提交的？」
7. **提前明确的收益**：出包前一条 `git status` 断言（干净或白名单残留）即可让"已交付"与"已提交"永不脱钩；本轮收尾提交本质是补作业。

### G-R2-3 ｜配对码「三台刚配完就取消」：安全需求没先问场景

1. **原来怎么说**：1.1.29(11-07) 专门做了「三台生产包配置服务器主备地址与配对码」（`evidence-2026-11-07-version-push/QA_RESULT.md:9`），Note 12 还因配对码输入框踩了软键盘黑屏坑（同文件:35）。
2. **后来实际怎样**：仅一天后 1.1.32(11-08) 取消 32 位配对码，局域网/Tailscale/本机自动签发凭据（`evidence-2026-11-08-auto-pair/QA_RESULT.md`；`docs/risks.md:40`）。
3. **差在哪里**：威胁模型没先定——把"公网级"的配对码安全默认套在"家庭局域网"场景，用户痛点（填码繁琐、软键盘黑屏）本可一问即知。
4. **为何本应提前思考**：服务从 Day 1 就只在家里 Wi-Fi/Tailscale 用，「同网设备要不要互信」是开工第一天的架构问题。
5. **不提前造成何种返工**：1.1.29 一整轮"配码＋配对"的出包、装机、踩坑记录作废一天即弃；且新方案把安全边界放宽为「同网任意设备可获曲库读写」（`docs/risks.md:40`），是需要用户知情的安全取舍。
6. **下次普通人怎么说**：「家里 Wi-Fi 里的手机连曲库，要不要密码？客人手机连上能不能动我的歌？」
7. **提前明确的收益**：一问省一轮版本；安全边界（放宽到什么程度）由用户签字而非事后补记风险。

### G-R2-4 ｜QA 隔离库并入生产：为一次测试永久模糊数据边界

1. **原来怎么说**：上轮起一以贯之的纪律是「副作用验证用隔离副本，生产库前后哈希一致」（矩阵各节环境注记，如 `docs/qa/产品验收追踪矩阵.md:19,40`）。
2. **后来实际怎样**：2026-11-03 为让 Note 12 Pro 真机测导入，把生产库 31 首舞蹈/节目单/谱件/示例与 107 个媒体文件并入 real-qa（`docs/risks.md:8`）。
3. **差在哪里**：真实设备测试需要真实数据，但方案选了"把生产搬进 QA 库"而不是"给真机指一个只读视图/再克隆一份生产库"；从此 real-qa 既是 QA 库又是生产库。
4. **为何本应提前思考**：真机验收必然要真实数据（L2 教训），"真机测试环境怎么供数"应在 1.1.x 真机化一开始就设计。
5. **不提前造成何种返工**：此后所有"隔离库重置"类清理动作永久失效；回退需恢复备份并清理新增媒体（`docs/risks.md:8`），操作前还要单独确认。
6. **下次普通人怎么说**：「测试用的库和真库分开了吗？别哪天清测试数据把我的歌清了。」
7. **提前明确的收益**：定一条"真机验收库=生产库的只读克隆，每轮重建"即可保住隔离纪律，省去永久性风险登记。

### G-R2-5 ｜验收债被"用户喊停"搁置而非清偿：未测 AC 无清偿机制

1. **原来怎么说**：矩阵规则「单元测试/构建/代码审查通过不代替产品验收；每条 AC 必须有可回访证据」（`docs/qa/产品验收追踪矩阵.md:7`）。
2. **后来实际怎样**：AC-LRC-04/NAV-04/NAV-07（窄屏/字号/横屏/返回栈）、AC-PRINT-04（黑白打印）、断网播放复测自 11-04 起持续未测；11-08 用户指示「其余待办本轮全部不做」（`HANDOFF.md:5,19`）；账本上 36 行 `chain_status=OPEN`（grep 实测计数，`docs/model/TASK-MODEL-LOG.jsonl`）。
3. **差在哪里**：未测项都如实标了（这点合格），但没有任何机制决定"欠到什么时候必须还"——搁置靠用户喊停，而不是到期自动升级。
4. **为何本应提前思考**：窄屏/横屏/返回栈是移动端一次性验收成本，拖到三个版本之后代码越叠越难归因。
5. **不提前造成何种返工**：`docs/risks.md:8` 型"改完 A 修复 B 复发"风险随代码量放大；一旦后续真在 360dp 机器上出问题，排查面覆盖 1.1.22 以来全部改动。
6. **下次普通人怎么说**：「这些没测的项，是打算永远不测，还是哪个版本之前必须补上？」
7. **提前明确的收益**：把"债"变成"有期限的待办"，可避免长期 OPEN 项在账本上无限累积（现有 36 行 OPEN）。

### G-R2-6 ｜工作区收尾不净：来源不明的删除悬置

1. **原来怎么说**：交接纪律要求收尾核对工作区（工作区根 AGENTS「不覆盖用户未提交代码」；HANDOFF 记「业务与文档改动已全部提交」，`HANDOFF.md:31`）。

## 6. 根因追溯（四类，追到根因为止）

**UI/交互**
- 现象：1.1.31 点倍速/循环后按钮行上下挪动。链：状态行凭空多一行（文档流插入）→ `.vocal-practice.is-immersive .vocal-dock`（特异性 0,2,1）的 `position:static` 覆盖 `.vocal-dock--immersive`（0,1,0），浮层包含块失效被顶出视口（`evidence-2026-11-07-loop-rap/QA_RESULT.md:86`）。**根因：项目没有"瞬时反馈不得参与文档流、浮层包含块唯一"的交互约定，每处提示各写各的，靠验收兜底。**
- 现象：四台设备坐标点按偏移、误触。链：截图缩放尺寸换算错＋用户占用焦点。**根因：真机自动化没有"点击前后断言前台 App＋按 `wm size` 换算"的标准动作（已在 `agent.md:80` 沉淀，属事后补）。**

**操作体验**
- 现象：配对码填码繁琐、Note 12 软键盘黑屏两连。**根因：安全模型（公网级配对）与真实场景（家庭局域网互信）错配；输入法兼容问题则是 WebView 在 MIUI 上的已知生态债，无兜底（如先验证码后输码的免键盘路径）。**

**外部依赖**
- 现象：《绿光》高亮"差一句"。链：网易云 LRC `startMs` 比真实起唱晚 0.4–10.7s 且无规律（`evidence-2026-11-06-lyric-timing/QA_RESULT.md:11`）→ 高亮永远落错行。**根因：导入管线把外部 LRC 时间戳当可信数据，没有"导入时音频级锚点抽检"门；文本完整≠时间正确，字段级校验只查了文本。** 同根延伸：DERP(sfo) 14–36 KB/s 在线听不可用、《绿光（抖音热播）》卡在客户端下载（`HANDOFF.md:51-52`）——外部源无 SLA，但至少"不可用"被如实报告，未编造。
- 现象：NCM 转 mp3 字节正常却不能播、文件名解析冲突（`agent.md:28-29`）。**根因同上：以"表面指标"（大小/文件名）代替"内容校验"（ffprobe/解析规则）。**

**质量验证**
- 现象：AC-PRINT-05 假 PASS；release 包无 CDP，真机交互验证降级为截图坐标点按（`evidence-2026-11-07-loop-rap/QA_RESULT.md:69`）；窄屏/横屏/返回栈三个版本未补测。**根因有三层：①判据写"表象"不写"结果"，与 agent.md 铁律脱节；②验收方式单点依赖 CDP，CDP 不可用时没有替代的 DOM 取证通道（只降级不换道）；③OPEN 项无期限、无升级机制，验收债靠用户喊停（G-R2-5）。**

## 7. 通俗需求表达问题（普通用户可直接回答）

1. 手机上要不要能"把 A4 稿存成文件/打印"？还是只在电脑上打印就够了？
2. 家里 Wi-Fi 里你自己的手机连曲库，要不要输配对码？客人的手机连上要不要限制？
3. 手机没网时，哪些歌必须能放？整份"想学"歌单要不要都缓存？
4. 像"歌词差一句"这种要靠耳朵的问题，最后由你本人听一遍确认，还是我们自动核对就算过？
5. 三台手机，验收用一台代表就行，还是每台都要完整过一遍？
6. "跳过 Rap""循环 3/5 句"这类功能，验收标准是按钮都能点，还是你真用它练歌觉得顺手？
7. 拍纸稿自动改歌词，要不要接付费的图像识别服务？纸稿照片可以发到云端吗？
8. 版本新旧，你自己在"设置→关于"里核对，还是每次由我们报给你？
9. "想学"歌单导入是整单全导，还是每首要你点头？
10. 出门用流量在线听歌（现在很慢），值得花钱自建服务器吗？
11. 小屏、系统大字号、横屏、安卓返回键这些"角落场景"，要不要列入每轮必测？
12. 黑白打印出来的效果，要不要真打一张给你看？

## 8. 开工前体检表（针对本项目类型：本地服务＋多真机 APP/PWA）

1. [ ] 出包前 `git status` 干净（或残留逐项白名单）；脏树不出包
2. [ ] 每次出包跑 `android:bump`，装机后"设置→关于"回读版本核对
3. [ ] 认包以 SHA-256，不以版本号（同版本多包教训）
4. [ ] 文件落盘类功能的判据＝"设备文件系统找得到＋外部应用能打开"，不是界面提示
5. [ ] 每个用户可见交互改动至少一台真机走查并留截图；多台交付时写明哪台全量、哪台抽检
6. [ ] 外部歌词/音频导入时做一次音频级锚点抽检（文本完整≠时间正确）
7. [ ] "要不要做"存疑的能力（打印/配对/识别）先问再做；做了之后否决的功能写明代码处置
8. [ ] 安全边界变化（免配对/免登录/放宽来源）先写明"谁能连、能干什么"并请用户确认
9. [ ] 真机供数方案：生产库只读克隆，不把 QA 库与生产库合并
10. [ ] 自动化 PASS ≠ 真机 PASS；release 包无 CDP 时预留调试通道或明示降级取证方式
11. [ ] 未测 AC 标 OPEN/BLOCKED 并带期限；账本 OPEN 行定期清点
12. [ ] 服务重启/常驻化前确认无他人在跑验证；改动登记后台服务表
13. [ ] SQLite 备份用 `.backup`＋`integrity_check`＋计数对齐，不用 `cp`（WAL 半份备份坑）
14. [ ] AI 生成物（译文等）固定抽审比例并留复核记录；判分母用 `translatableLines` 口径
15. [ ] 收尾时 `git status` 逐项清零或写明归属；刚交付功能的文件异常删除必须当场查明

## 1. 跨项目可复用教训（按优先级）

### L1 · 已提交 = 可部署（可复现性治理铁律）
- **定案**：HEAD 最高版本号 = 9（1.1.6），但工作树已到 15（1.1.12），1.1.7–1.1.15 全部来自未提交树。`git rev-list HEAD -- android/app/build.gradle` 实测有 **3 个提交**（2ca15cd 初建/784da4f bump/eb748f7 1.1.6）触碰过该文件——A V1.1 称"仅 eb748f7"为事实错误，但核心结论（所有更高版本均不可复现）成立。
- **归类**：非狭义"返工"，属**可复现性治理失效**（代码未浪费，仅未固化、不可回溯）。
- **Day 1 该说**：「任何要装到用户手机/上线的包，必须来自已 `commit` 的 HEAD；调试包版本号须与 HEAD 一致，禁止用脏工作树出包。」

### L2 · 真实样本出声硬 gate（一次性交付 QA 根因）
- **定案**：V2.1 用 5 首原创 demo 替代用户真实节目单 5 首，真实五首全程未出声（HANDOFF:10/18/21 实证）。
- **Day 1 该说**：「验收不看截图、不看 demo。交付硬 gate = 用户的**真实**样本在**真机**真出声/真显示。demo 只是开发自测，不算验收通过。」

### L3 · 范围先定，再动手（多才艺三次叠加返工源）
- **定案**：项目名"才艺展示厅"暗示多才艺，但 001 只做舞蹈；002 追加吉他+唱歌、003 三才艺完整化，每次独立规格分支。`003` 计划明确"不把旧 DanceItem 硬改成全才艺实体"。
- **Day 1 该说**：「先确认：只做舞蹈，还是多才艺（舞蹈/吉他/唱歌）？若多才艺，数据模型第一天就按 `ItemRef` 多类型抽象写基线，别事后打补丁。」

### L4 · 非目标清单 + 动手前确认"做不做"（边界澄清缺口）
- **定案（两路共识降级）**："伴奏/音源分离"Day 1 与 001 均无约束；V3.1 把它当"待执行功能"设计（产出了 `tool/run_separation.py`，已提交 `eb748f7`），**直到 V3.2 才由用户新指令显式"不做"**。B V1.0 原归"Agent/流程失误"过重，两路同意降级为"迭代中才澄清的边界 + 可预防的前提确认缺口 + 正常迭代"。
- **Day 1 该说**：「列一张'明确不做'清单；凡清单外的探索性能力（如伴奏分离），动手前先书面确认'做不做'，别默认做。」

### L5 · 每加一种才艺，先写形式化 spec.md（B 独有贡献 G2）
- **定案**：实测 `specs/001` 有 `spec.md`，`specs/002`、`specs/003` 均**无** `spec.md`；A V1.0 漏列，经 B V1.0 揭示、A V1.1 §12 承认补入。
- **Day 1 该说**：「扩展规格必须走形式化 spec 模板（目标/范围/非目标/验收），禁止'先写代码再补文档'。」

### L6 · UI 真机验收未闭环，统标"待验证"（B 独有贡献 G6）
- **定案**：HANDOFF V1.2 自承"未上手机/未视觉走查"；001 spec SC-008 有真机视觉检查却未执行。界面若未实机验收，应统标"待验证"，不能凭代码判用户满意。
- **Day 1 该说**：「每个界面交付前必须真机走查并留痕；未走查的条目在验收单标'待验证'。」

### L7 · AI 出稿 + 人工抽审（译文等生成物验收边界，B 独有贡献 G8）
- **定案**：HANDOFF"语义未全面人工审核（首批5首292行改73行；第二批895行未逐句复核）"；`.env.example` API_KEY 空。
- **Day 1 该说**：「AI 生成的译文/内容，验收口径是'AI 出稿 + 人工抽审'，写明抽审比例，不能默认全自动正确。」

### L8 · 生产库迁移作为发布前硬 gate（数据态与代码态脱节）
- **定案**：代码已依赖 0010 schema，生产 DB 仍停在 0006；已部署代码与生产数据长期脱节，迁移无限期"待授权"。
- **Day 1 该说**：「schema 迁移纳入发布前硬 gate；'代码依赖 N 版本但生产库还在 M 版本'视为未发布完成。」

### L9 · 应用名 ≠ 项目名，命名与首形态错位（B 新增 G14）
- **定案**：立项 README（`e198c06`）"具体产品方向待后续明确"，首个真实规格是"个人舞蹈曲库 V1.5"；应用名实际为"舞蹈曲库"，与项目名"才艺展示厅"不一致。
- **Day 1 该说**：「立项时确认产品真名与首发形态，命名误导会放大后续范围漂移。」

## 3. 开工前体检表（给下一个同类项目）

1. [ ] 产品真名与首发形态已确认，命名不误导范围
2. [ ] 范围清单：只做 X / 多类型（已按多类型抽象基线）
3. [ ] 非目标清单已列；探索性能力动手前书面确认"做不做"

5. [ ] 已提交 = 可部署：出包版本号 == HEAD，禁止脏树出包

8. [ ] AI 生成物验收口径 = AI 出稿 + 人工抽审（写明比例）
9. [ ] schema 迁移纳入发布前硬 gate；代码态 == 生产数据态
10. [ ] 首次发布 Human Gate 签收不为 OPEN；验收口径书面化

## 5. 一句话总判

040 的最大教训不是"某次返工"，而是**四态长期脱节 + 范围/边界在迭代中才澄清却无机制捕获**。Day 1 提示词若内置 L1–L9 九道 gate，可把本项目的可预防返工压缩到接近零；其余（多才艺抽象、伴奏分离探索）属正常迭代，不应误判为开发者失误。

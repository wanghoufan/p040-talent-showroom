## 1. 现象

| 层 | 事实 |
| --- | --- |
| 扫描 | `issues = ["audio-role-unmarked-original-assumed","audio-tail-truncated"]`；`decode.state = tail-truncated` |
| 提取 | 3 次 attempt 全部 `SEPARATOR_FAILED`（退出码 1），attempt 1/2/3 分别耗时 3s / 3s / 3s |
| 产物 | `media/vocal-import/78aef09f-…5558a/` 下 3 个 run 目录**全空**，没有 `original.mp3`，没有任何 stem |

关键区分：**`audio-tail-truncated` 只是告警，不是失败原因**。它不在 `server/vocal-import/issues.mjs:8-22` 的 `REVIEW_ISSUES` 白名单里，`needsReview()` 返回 false，`scan.mjs:324` 会把这首歌判为 `ready-to-extract`。任务变成 `FAILED` 只因为分离器进程退出码 1。这两件事必须分开看，否则容易误判成「扫描太严把好文件拦下来了」。

### 2.5 体积自洽性

| 项 | 数值 | 说明 |
| --- | --- | --- |
| 声明 191.132834s @320kbps 应有音频字节 | 7,645,313 | 40,000 B/s |
| Xing 声明字节 | 7,647,607 | 与上式一致 |
| 实际存在音频字节 | 7,552,522 | 差 95,085 字节 ≈ 2.32 s |
| 文件总大小 | 7,959,320 | = ID3v2 头及封面 312,757 + 真实音频 7,552,522 + 全零尾巴 94,041 |

**体积不矛盾，字节数甚至「看起来完整」**（正好等于「完整音频 + 封面」的大小），但其中 94,041 字节是 0x00。这是典型的「预分配/占位后写入中断」：文件长度到位，尾部内容没落地。所以不能用「文件大小对不对」来判断完整性，必须看覆盖率——项目的做法是对的。

## 3. 阈值定位

| 项 | 位置 | 表达式 |
| --- | --- | --- |
| 完整解码阈值 | `server/vocal-import/probe.mjs:21` | `export const FULL_DECODE_MIN_COVERAGE = 0.999;` |
| 尾部损坏下限 | `server/vocal-import/probe.mjs:20` | `export const TAIL_DAMAGE_MIN_COVERAGE = 0.95;` |
| 判定链 | `server/vocal-import/probe.mjs:124-127` | `!decodedMs → failed`；`errors==0 && (cov===null \|\| cov>=0.999) → ok`；`cov>=0.95 → tail-truncated`；否则 `damaged` |
| 覆盖率计算 | `server/vocal-import/probe.mjs:116-118` | `coverageRatio = min(1, round(decodedMs/durationMs*10000)/10000)` |
| 上游 issue 映射 | `server/vocal-import/scan.mjs:228` | `if (decodeState === 'tail-truncated') issues.push('audio-tail-truncated')` |

本文件实测：

```
durationMs = 191133           (191.132834 s)
decodedMs  = 188788           (3,020,608 B / 2 / 8000)
coverage   = 188788 / 191133 = 0.9877   ← 与 real-music-audit-deep.json 的 0.9877 完全一致
```

- 距 `0.999` 差 **0.0113（1.13 个百分点）**，需要再多解 **2.154 s** 才达标；实际缺失 **2.345 s**。也就是说 0.999 本身给的 0.19 s 容差完全不够填这个洞。
- 距 `0.95` 高 0.0377，所以落 `tail-truncated` 而不是 `damaged`——归类是对的：坏的确实只有尾部。

## 4. 三问结论

### a. 源文件是否损坏/不完整 —— **是，不完整（尾部 2.345 s 是全零占位，非音频）**

证据链闭合：Xing 头声明 7,318 帧，实际只有 7,227 帧，缺 91 帧 ≈ 2.3 s；缺口位置正好是文件末尾 94,041 字节的纯 `0x00` 区。这不是编码器产物、不是 DRM、不是容器封装差异，是**内容根本没写进去**。转码无法补回，任何 DSP 都造不出不存在的采样。

### b. 阈值是否过严 —— **不是。这次判定正确，不建议调阈值**

- 缺口是 1.13 个百分点 / 2.345 秒真实音频，不是「只差 0.1%」的抖动。
- 对照组（同 batch-10 的其余 9 首，见 `control-coverage-batch10.tsv`）覆盖率全在 0.9999–1.0000、0 条解码报错：

  | 文件 | 声明 s | 解码 s | 覆盖率 | 报错 |
  | --- | --- | --- | --- | --- |
  | 4MINUTE - 미쳐 | 191.133 | 188.788 | **0.9877** | 1 |
  | 其余 9 首 | 171–234 | 同声明 | 0.9999–1.0000 | 0 |

  同一台机器、同一组命令，只有这一首掉下来，说明阈值没有误伤正常文件。
- 即便把阈值降到 0.98 让它「通过扫描」，**也修不好它**：失败发生在分离器，不是扫描（见 c）。调阈值只会让一个坏文件带着 2.3 s 静音尾巴进库，属于掩盖问题。

> 附带发现（不在本次修改范围，仅记录）：`scan.mjs:226-228` 的设计意图是「尾部少量损坏可继续提取」，但下游 `audio-separator` 显然不容忍这种输入。等于允许一类注定在 EXTRACT 阶段炸的文件进入队列，白烧 3 次 attempt。这是「扫描宽容度」与「分离器容忍度」不一致，属于设计口径问题，不是本次阈值数值问题。

### c. 转码成 wav/flac 能否通过现有校验 —— **能，但那是「把缺陷洗白」，不是修复**

实测（`var/vocal-v31-work/diagnose-michi/michi-reencoded.flac`，52.8 MB）：

```
$ ffmpeg -v error -nostdin -y -i "<src>" -map 0:a:0 -c:a flac -compression_level 5 michi-reencoded.flac
（仍打印同一条 mp3 坏包报错，但 flac 正常产出）

flac declared = 188.788 s
flac decoded  = 188.788 s
coverage = 1.0000, errors = 0  →  probeState = ok
```

机制：转码时 ffmpeg 只写「能解出来的部分」，产物的容器时长随之缩到 188.788 s，覆盖率分子分母同时变小，自然等于 1。**通过校验靠的是声明时长变短，不是音频变全** —— 那 2.345 s 尾奏依然永久丢失。

另外，转码产物在 ffmpeg 口径下 0 报错、可完整解码，如果分离器崩溃确实源于输入尾部全零，换成这个 flac **大概率能过 EXTRACT**（本次受「GPU 占用、不得跑分离」约束，未实跑验证，此句为推断）。

### d. 分离器为什么退出码 1（未完全取证）

- 已确证：3 次 attempt 各约 3 s 就退出（14:32:08→11 / 12→15 / 15→18），产物目录全空。
- 3 秒 ≈ 模型加载 1.5 s + 立即失败，**排除慢、排除超时、排除 OOM 式的长尾失败**；三次耗时几乎相同，是**确定性失败**，指向输入文件本身而非资源竞争。
- 最可能：`audio-separator` 用 soundfile/libsndfile 读输入，遇全零 MPEG 帧直接抛错退出（交叉验证日志 `logs/en-crosscheck.log:17-18` 可见它确实走 soundfile 且能识别 `MPEG_LAYER_III`）。
- **但 `server/vocal-import/separator.mjs:190` 的 `logger.error` 只把 stderr 打到进程输出，没有落盘**，本次在 `temp/server-8791.log`、`var/vocal-v31-work/logs/*` 里都找不到该 job 的 stderr。所以「输入解码失败」是推断，不是取证结论。若需坐实，最小代价是下次复现时把分离器的 stderr 保存成 job 级日志（这是可观测性缺口，不是本文件的问题）。

## 5. 处置建议

**三选一：重新获取源文件。** 理由：

1. 丢的是真实音频（末段 2.345 s），只有重新下载/重新导出能补回；转码、调阈值都只是绕过检测。
2. 调阈值不但无效（失败在分离器，不在扫描），还会引入「把坏文件放行」的长期风险——本批其余 9 首都贴着 1.0000，阈值本身没有误伤。
3. 重新获取后，用同一口径自检即可确认：（期望）覆盖率 ≥0.999、`ffmpeg -v error -i … -f null -` 0 行输出、末尾 94 KB 不再是全零。

备选（仅当原文件确实拿不到，且业务能接受歌曲最后 2.3 s 尾奏缺失）：按 `michi-reencoded.flac` 的方式转码成 FLAC 后重入，并在人工备注里写明「尾段 2.345 s 缺失，已转码规避」。这是有损的合规绕行，不是修复，必须留痕，不能当成默认处理方式。

不建议：直接把 `TAIL_DAMAGE_MIN_COVERAGE` / `FULL_DECODE_MIN_COVERAGE` 调低。
